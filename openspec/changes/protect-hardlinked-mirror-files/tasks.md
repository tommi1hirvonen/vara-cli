## 1. FileSystemContentStore: mark hardlinked mirror entries read-only

- [x] 1.1 In `FileSystemContentStore.PlaceAtMirrorPath`, after `Kernel32.CreateHardLink(stagingPath, blobPath)` succeeds (both the direct hardlink branch and the branch where a hardlink attempt succeeds after a previously forced/per-blob failure), set `File.SetAttributes(stagingPath, File.GetAttributes(stagingPath) | FileAttributes.ReadOnly)` on the staged file before the final `File.Move`.
- [x] 1.2 In the copy-fallback branch (`CopyWithProgress` call, both the no-hardlink-support case and the hardlink-attempt-failed case), explicitly ensure the staged file is not read-only (e.g. clear `FileAttributes.ReadOnly` if present on the newly-created staged file) so a stale attribute can never leak through, even though a fresh `FileMode.CreateNew` file should not carry it by default.
- [x] 1.3 Immediately before the final `File.Move(stagingPath, mirrorPath, overwrite: true)` in `PlaceAtMirrorPath`, if `mirrorPath` already exists and currently has `FileAttributes.ReadOnly` set, clear that attribute on `mirrorPath` first (`File.Move` throws `UnauthorizedAccessException` when overwriting a read-only destination on Windows/.NET - verified empirically; see design.md). Verify the moved-in file still ends up with the *new* placement's own attribute (from the staged file), not the cleared one.
- [x] 1.4 In `FileSystemContentStore.RemoveFromMirror`, before `File.Delete(mirrorPath)`, if `mirrorPath` currently has `FileAttributes.ReadOnly` set, clear that attribute first (`File.Delete` throws `UnauthorizedAccessException` against a read-only target on Windows/.NET - verified empirically).

## 2. Restore protection after a clear-and-mutate (the shared-attribute fix)

- [x] 2.1 Change `IContentStore.RemoveFromMirror`'s signature to `RemoveFromMirror(string mirrorRelativePath, string hash)`, updating its doc comment to explain `hash` identifies the content whose blob file must be re-protected after the mirror entry is removed.
- [x] 2.2 Change `IContentStore.PlaceAtMirrorPath`'s signature to add an optional trailing parameter `string? previousContentHash = null`, updating its doc comment to explain this identifies the content previously at `mirrorRelativePath` (if any), whose blob file must be re-protected after the overwrite.
- [x] 2.3 In `FileSystemContentStore.RemoveFromMirror`, after successfully deleting `mirrorPath`, if `BlobPath(hash)` still exists, ensure it has `FileAttributes.ReadOnly` set (add the flag if not already present) - restoring protection for that content's canonical blob file and any other mirror path still deduplicated against it (NTFS shares the read-only attribute across all hardlinks to the same data - see design.md).
- [x] 2.4 In `FileSystemContentStore.PlaceAtMirrorPath`, after the final `File.Move` completes, if `previousContentHash` is non-null and `BlobPath(previousContentHash)` still exists, ensure it has `FileAttributes.ReadOnly` set, the same way as task 2.3.
- [x] 2.5 In `FileSystemContentStore.DeleteContent`, before `File.Delete(blobPath)`, if `blobPath` currently has `FileAttributes.ReadOnly` set, clear that attribute first (a blob can now be read-only as a side effect of tasks 1.1/2.3/2.4; `PruneService`'s existing reference-counting already guarantees nothing else references this blob, so no restore-after step is needed here).
- [x] 2.6 In `FileSystemContentStore.TryDelete` (used by `CleanupOrphanedTemp` and `ProbeHardlinkSupport`'s own cleanup), clear `FileAttributes.ReadOnly` first if present, before attempting `File.Delete`, so a staged file orphaned by a crash between task 1.1's attribute-setting and the final move can still be cleaned up.
- [x] 2.7 Add a private helper (e.g. `EnsureReadOnlyIfPresent(string path)`, mirroring the existing `ClearReadOnlyIfPresent`) used by tasks 2.3/2.4 to avoid duplicating the "get attributes, add the flag, set attributes" logic.

## 3. Plumb the previous content hash through the backup pipeline

- [x] 3.1 Add a `PreviousContentHash` field to `PlannedOperation` in `BackupModels.cs` (nullable `string`, default `null`), with a doc-comment note that it is populated only for `Change` operations, from the current manifest state's content hash - already known at plan time, distinct from `KnownContentHash` (which is the *new* content's hash, not known until execution for `Add`/`Change`).
- [x] 3.2 In `BackupPlanner.Plan`, when constructing a `PlannedOperationKind.Change` operation, populate `PreviousContentHash` from `currentState[change.Entry.RelativePath].ContentHash` (the same `currentState` dictionary already in scope and already used for move detection); leave it `null` for `Add`.
- [x] 3.3 In `BackupExecutor.ExecuteMoveOrDelete`'s `Delete` branch, pass `operation.KnownContentHash!` as the new `hash` argument to `contentStore.RemoveFromMirror`.
- [x] 3.4 In `BackupExecutor.ExecuteTransfer`, pass `operation.PreviousContentHash` as the new `previousContentHash` argument to `contentStore.PlaceAtMirrorPath`.
