## Context

See proposal.md - Why. `PlaceAtMirrorPath` (`src/Vara.Infrastructure/Storage/FileSystemContentStore.cs`) currently has two placement paths that converge on the same final step - `File.Move(stagingPath, mirrorPath, overwrite: true)`:

- **Hardlink path** (`SupportsHardlinks` true, and no forced/per-blob failure): `Kernel32.CreateHardLink(stagingPath, blobPath)` stages a hardlink to the blob, then the atomic rename places it at `mirrorPath`. The resulting mirror file *is* the blob (same physical file/inode).
- **Copy-fallback path** (`SupportsHardlinks` false, or the hardlink attempt threw `IOException` - most notably NTFS's 1024-hardlink-per-file cap): `CopyWithProgress` streams the blob's bytes into a brand-new file at `stagingPath`, then the same atomic rename places it. The resulting mirror file is an independent physical copy.

Today neither path touches `FileAttributes` at all - both produce a normal writable file. Per the existing "Graceful degradation when a blob's hard-link limit is reached" requirement, which of the two paths executes for a given mirror path can differ from one run to the next (a hardlink attempt can fail on one run, e.g. due to hitting the cap, and succeed on a later run once other paths referencing that blob are removed).

**Critical NTFS fact, verified empirically (not assumed):** `FileAttributes.ReadOnly` is stored once per underlying file record (MFT record) and is shared by *every* hardlink/name pointing at that record - it is not a per-link property. Setting or clearing it via any one hardlink's name immediately changes what every other hardlink to the same data reports, including the canonical blob file itself (`BlobPath(hash)` under `.vara\versions\`) and any *other* mirror path currently deduplicated against the same content. This was discovered during implementation and invalidated this design's first two drafts, which assumed read-only could be scoped to "just this mirror path." It cannot - the fixes below are built around that constraint instead of fighting it.

## Goals / Non-Goals

**Goals:**
- Mark a mirror entry read-only exactly when it is produced by the hardlink path, so an in-place naive overwrite fails at the OS level instead of silently mutating the shared blob.
- Keep a copy-fallback mirror entry writable, since it carries no shared-corruption risk.
- Keep the read-only attribute correct across runs even when a given mirror path's placement kind flips between hardlink and copy-fallback.
- When an operation must clear the shared read-only attribute to delete or overwrite one specific hardlinked name, restore it afterward on every content this change is responsible for protecting - including a deduplicated sibling mirror path or the canonical blob file - not just leave protection intact for the one name being directly operated on.
- Do not disturb `MoveMirrorEntry`, which must keep working on read-only entries exactly as it does today on writable ones, without needing any read-only-clearing logic of its own.
- Keep hardlink-based deduplication itself completely unchanged - no reduction in when content is shared via hardlink, no new duplication introduced for the common case of an unmodified or newly-added file.

**Non-Goals:**
- Detecting or reporting after the fact that a read-only mirror file was tampered with (e.g. via `attrib -r` followed by an edit) - out of scope; the read-only attribute is a friction/signal mechanism, not an enforced security boundary, and a determined user can always clear it.
- Any change to `ExtractTo` (single-file restore-to-arbitrary-location) or to how a migrated/copied mirror is made writable again on a new machine - those already fall outside `PlaceAtMirrorPath`, and clearing the attribute recursively is a standard Windows Explorer/`attrib` operation the user performs deliberately, not something Vara needs to automate.
- Cross-platform semantics beyond what .NET's `FileAttributes.ReadOnly` / `File.SetAttributes` already provide on Windows (Vara targets Windows per README).
- Any new low-level Win32/NT interop (e.g. `FILE_DISPOSITION_INFO_EX`'s `FILE_DISPOSITION_FLAG_IGNORE_READONLY_ATTRIBUTE`) - considered and rejected in favor of the "clear, mutate, restore via a known surviving name" approach below, which achieves full correctness using only `File.GetAttributes`/`File.SetAttributes` and content hashes the backup pipeline already computes.

## Decisions

**Set the attribute on the staged file before the atomic rename, not on the final mirror path after it.** `CreateHardLink`/`CopyWithProgress` both write to `stagingPath` first; `File.Move(stagingPath, mirrorPath, overwrite: true)` then does the atomic swap. Setting `FileAttributes.ReadOnly` on `stagingPath` immediately after it's populated (hardlink created, or copy completed) keeps the attribute change inside the same "prepare, then atomically swap" structure the method already uses for crash-safety, rather than adding a second, separate filesystem call after the rename that could itself be interrupted, leaving a hardlinked mirror file transiently writable.

**Clear a pre-existing destination/target's read-only attribute before `File.Move` (overwrite), `File.Delete`, and orphaned-temp-file cleanup.** Verified empirically: on Windows/.NET, `File.Move(src, dest, overwrite: true)` and `File.Delete` both throw `UnauthorizedAccessException` against a read-only destination/target, rather than silently succeeding. Every place that deletes or overwrites a path that can carry this change's read-only attribute must clear it first: `PlaceAtMirrorPath`'s final overwrite of an existing mirror path, `RemoveFromMirror`'s deletion of a mirror path, `DeleteContent`'s deletion of a blob file (blobs can now be read-only too - see below), and `TryDelete`'s best-effort cleanup of an orphaned staged temp file (a crash between marking a staged file read-only and its final move could leave one behind). `MoveMirrorEntry` is the one exception: it renames an entry to a *new, not-yet-existing* destination path (verified empirically), so a read-only *source* file is moved successfully without any attribute handling, carrying its own attribute forward as-is.

**Restore read-only on the relevant blob file after any clear-and-mutate, using a content hash the caller already has.** Because the read-only bit is shared per underlying file (not per hardlink name), clearing it to delete or overwrite *one* mirror path's name can leave *other* surviving hardlinks to the same data - a deduplicated sibling mirror path, or the canonical blob file itself - permanently writable unless something re-asserts the attribute afterward. The fix does not require tracking "was this specific mirror path a hardlink": it is always safe and correct to unconditionally (re-)assert `FileAttributes.ReadOnly` on `BlobPath(hash)` after the mutation, whenever that blob file still exists, regardless of whether the mirror path being mutated happened to be a hardlink or a copy-fallback entry - a copy-fallback entry's own attribute clear never touches the blob's attribute in the first place, so this is a no-op in that case rather than a correctness risk. Two call sites need a content hash to do this:
  - **`RemoveFromMirror` (file deleted):** `BackupExecutor` already has the deleted file's hash (`PlannedOperation.KnownContentHash`, already populated for `Delete` operations per the existing doc comment) - `RemoveFromMirror`'s signature gains a required `hash` parameter, used to restore protection on `BlobPath(hash)` after deleting the mirror entry.
  - **`PlaceAtMirrorPath` (file changed):** the *previous* content's hash was not previously tracked anywhere past the diff stage for a "Changed" operation (only `Add`/`Change`'s *new* hash is resolved, during execution) - but `BackupPlanner.Plan` already holds the previous hash in memory at zero extra cost, in the same `currentState` dictionary already used for move detection (`currentState[change.Entry.RelativePath].ContentHash`), simply never carried past the diff stage today. `PlannedOperation` gains a `PreviousContentHash` field (`null` for `Add`/`Move`/`Delete`, populated for `Change`), threaded through `BackupExecutor` into a new optional `previousContentHash` parameter on `PlaceAtMirrorPath`, used the same way after the overwrite completes.

  This closes the gap fully, including the deduplicated-sibling case: restoring read-only via `BlobPath(hash)` affects every hardlink sharing that inode, not just the blob's own canonical name, since the attribute is shared regardless of which name is used to set it.

**Blobs can now end up read-only too, as a side effect - `DeleteContent` and orphaned-temp cleanup must tolerate that.** No code explicitly sets `BlobPath(hash)` read-only on creation; it becomes read-only as a side effect the first time either (a) it's hardlinked into the mirror (the hardlink shares the attribute in both directions), or (b) a later clear-and-restore cycle (above) re-asserts it. Once that has happened, `DeleteContent`'s permanent blob deletion (used by `PruneService` garbage collection) must clear read-only before deleting, exactly like `RemoveFromMirror` - but never needs to restore anything afterward, since a pruned blob is gone entirely and by definition unreferenced by any live mirror path (`PruneService`'s existing reference-counting logic already guarantees this before calling `DeleteContent`).

**Always set the staged file's attribute explicitly for both branches, never rely on a prior run's leftover state.** Because `stagingPath` is a fresh temp file for every single call (`Path.Combine(_tempRoot, Guid.NewGuid().ToString("N"))`), there's no "leftover" attribute to inherit from a previous run on the *staged* file. Explicitly setting `stagingPath`'s attribute on every call (read-only on the hardlink branch, explicitly *not* read-only / default on the copy branch), combined with the destination-clearing and blob-restoring steps above, is sufficient to make every affected file correct on every call regardless of what it was before.

**Do not memoize placement-kind-to-attribute mapping across calls.** Consistent with the existing per-call (not per-blob) hardlink-vs-copy decision already documented in the method (a blob's link count isn't a stable fact), the read-only decision is likewise made fresh on every `PlaceAtMirrorPath` call from that call's own actual placement path, not cached or inferred from a prior call for the same mirror path or blob.

**Scope: two small `IContentStore` signature additions, no reduction in hardlink usage.** `RemoveFromMirror` gains a required `hash` parameter; `PlaceAtMirrorPath` gains an optional `previousContentHash` parameter (`null` by default, so any caller not tracking a previous hash - there is only one production caller, `BackupExecutor` - is unaffected for `Add`). Considered and rejected: falling back to a real copy instead of a hardlink for the "rare" deduplication case (two different files with identical content) - this does not address the actual hard case at all, since the previous-hash gap applies to *every* "Changed" file (the common case), not to deduplication specifically; abandoning hardlinks there would reintroduce the exact double-storage-per-change problem hardlinking exists to prevent, in violation of the existing "Content deduplication" requirement, while leaving the real problem (the Changed-overwrite case) unsolved.

## Risks / Trade-offs

- [A hardlinked mirror is now read-only almost everywhere on a typical NTFS target (every Add/Change placement hardlinks when `SupportsHardlinks` is true), so restoring/migrating the mirror to a new machine and treating it as a live working copy requires an explicit step to clear the attribute] → Accepted trade-off (see conversation/proposal): this is the intended signal that a backup mirror is not meant to be edited in place, and Windows Explorer's folder-level Properties dialog (or `attrib -R /S /D`) already provides a single, familiar, one-step recursive fix for a user who deliberately wants to convert a copy into an editable working tree. Not solved by this change; documented as expected behavior.
- [`File.Move(..., overwrite: true)` and `File.Delete` both throw `UnauthorizedAccessException` against a read-only *existing* destination/target on Windows/.NET - confirmed empirically during implementation, and initially missed by this design's first draft, which assumed the overwrite would silently succeed] → Mitigated by explicitly clearing the existing destination/target's read-only attribute before the move/delete call whenever it exists and is read-only (see Decisions), with test coverage asserting both that a "Changed" re-placement of an already-hardlinked mirror path succeeds and ends up with the *new* placement's correct attribute, and that `RemoveFromMirror`/`DeleteContent` succeed against a previously-hardlinked (read-only) target.
- [`FileAttributes.ReadOnly` is shared per underlying file across all hardlinks, not per link name - confirmed empirically, and initially missed by this design's second draft, which assumed clearing-then-restoring on the one mutated name was sufficient] → Mitigated by always restoring read-only via `BlobPath(hash)` after any clear-and-mutate operation (see Decisions), which correctly re-protects every surviving hardlink to that data (the blob's own canonical name and any deduplicated sibling mirror path), verified with dedicated test coverage for the deduplicated-sibling scenario.
- [A future change to `MoveMirrorEntry` could inadvertently assume mirror entries are always writable] → Mitigated by test coverage confirming `MoveMirrorEntry` still succeeds when its source is a read-only hardlinked entry (it never overwrites an existing destination in the normal-move case, so it needs no read-only-clearing logic itself), so a regression here is caught by the existing test suite rather than only surfacing as a field report.
