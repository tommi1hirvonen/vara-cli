## 6. Backup Pipeline (backup-execution)

- [x] 6.1 Implement the scan stage: recursive/non-recursive directory walk honoring excludes and glob patterns, recording (not following) symlinks/junctions/reparse points; verify with unit tests over a temporary directory tree covering excludes and a symlink. Used an NTFS junction (not a symlink) for the link test, since this dev environment cannot create real symlinks without elevated privileges/Developer Mode; junctions exercise the identical reparse-point code path. Glob matching uses `Microsoft.Extensions.FileSystemGlobbing`.
- [x] 6.2 Implement the diff stage: compare scanned entries against the manifest's current-state view by size and modification time, classifying each as unchanged/changed/added, and detect deletions (manifest entries with no corresponding scanned entry); verify with unit tests for each classification.
- [x] 6.3 Implement move detection: match a changed/added entry's content hash against a hash that disappeared from its previous path in the same run, treating it as a move rather than a delete+add; verify with a unit test moving a file between two directories. Move candidates are limited to `Added` entries matched by size first (cheap pre-filter), then hash - avoids hashing every changed file just to rule out a move.
- [x] 6.4 Implement the plan stage: aggregate the diff into an operation list with total bytes to transfer, excluding move/delete/hardlink-only operations from the byte total; verify with a unit test asserting the computed byte total reflects only genuinely transferred content. Because move detection is resolved during planning (not deferred to execution), the byte total is genuinely known before any transfer begins, satisfying the progress-reporting spec's "Upfront work estimation" requirement.
- [x] 6.5 Implement the execute stage: apply planned operations with bounded parallelism, isolate per-file failures (e.g. a locked file) so they are recorded without aborting the run, and write content via the atomic content-store path; verify with an integration test that includes an intentionally locked file and confirms the run still completes. Add/Change operations (the only ones with real source-disk I/O) run under `Parallel.ForEach` with a configurable degree of parallelism (default `Environment.ProcessorCount`); Move/Delete run sequentially first since they're cheap metadata-only changes. Manifest writes and counters are serialized under a lock (a single SQLite connection isn't safe for concurrent multi-threaded use); the content store's blob-creation race (two threads storing identical content simultaneously) is handled as a benign no-op. Verified with both a locked-file test and a 50-file bounded-parallelism stress test.
- [x] 6.6 Implement the commit stage: finalize the snapshot row (stats, `status = complete`) only after every planned operation has resolved (success or recorded failure); verify with a test that an interrupted run leaves the snapshot row as `running`, not `complete`. Implemented as `BackupPipeline`: an exception during scan/diff/plan/execute is caught, the snapshot is marked `failed`, and the exception is rethrown; an uncaught process termination leaves the row `running`, reconciled to `failed` at the start of the next run.
- [x] 6.7 Implement the per-profile run lock preventing concurrent runs against the same target; verify with a test attempting to start a second concurrent backup and asserting it is refused with a clear message. Implemented as `FileRunLock` (exclusive-share lock file under `.vara\run.lock`, auto-released on process exit/crash).
- [x] 6.8 Add an integration test that runs a backup twice against an unchanged source and verifies the second run performs zero content transfer.

## 9. Retention & Pruning (retention-pruning)

- [x] 9.1 Implement the tiered bucketing algorithm (daily/weekly/monthly/yearly, newest-per-bucket) that determines which snapshots are eligible for removal; verify with unit tests covering bucket boundaries and configured counts.
- [x] 9.2 Implement the `prune` command: apply the bucketing algorithm, delete eligible snapshot/file-version records, then run the unreferenced-content garbage collection to delete orphaned blobs; verify with an integration test asserting the expected snapshots and blobs remain after pruning a seeded history. **Correctness fix found during implementation:** pruning operates at the file-version-row level (`ISnapshotRepository.PruneSnapshots`), not whole-snapshot deletion - a row is preserved regardless of its snapshot's age if it is still the current state of its path, otherwise a file that hasn't changed recently would be silently orphaned from `GetCurrentState()`. A snapshot record is only removed once none of its rows remain. design.md updated to reflect this.
